# AXI2CHI Order Buffer 设计思路

## 1. 设计目标

本模块用于处理多个交织进入的 AXI 写事务，并完成 AXI 到 CHI 的事务转换与顺序管理。

核心约束如下：

- 相同 `AWID` 的事务必须按接收顺序发送和释放；
- 不同 `AWID` 之间没有顺序要求，可以根据 `QoS` 调整发送次序；
- `QoS` 为 1 bit，仅区分 High 和 Low 两类；
- 在满足同 ID 保序的前提下，尽量降低 High QoS 事务的等待时间；
- 设计需兼顾性能、功耗、面积、实现复杂度和时序稳定性。

当前事务参数如下：

| 参数 | 配置 |
| --- | ---: |
| Address | 48 bits |
| Data | 12 bits |
| AWID | 11 bits |
| QoS | 1 bit |

> Data 位宽按当前需求记录为 12 bits，后续应与 AXI/CHI 接口定义再次确认。

事务的主要处理流程为：

```text
AXI事务进入
    → 发送 CHI TXREQ
    → 等待 CHI RXRSP
    → 发送 CHI TXDAT / 生成 AXI BRESP
    → 完成事务并释放 Entry
```

对chi接口分为请求侧以及响应侧，两接口均有qos+保序的需求
两侧核心差异在于：

- 事务在请求侧的生命周期为：axi-aw-w握手 -> 排队等待 -> 发送仲裁 -> txreq。最大延迟由握手成功至credit good状态延迟决定。
- 事务在响应侧的生命周期为：写入节点-> rxresp返回 -> 保序等待 -> 发送仲裁 -> txdata/bresp。最大延迟主要由写入节点至响应返回的延迟决定。

从这两处差异可以引出为什么需要功能解耦：
如果不进行功能解耦，而由统一的链表或 Entry Pool 管理事务的完整生命周期，则每个 Entry 需要从 AXI AW/W 接收一直保留到 RXRSP 返回及 TXDAT/BRESP 完成。其容量需要按照峰值吞吐率、端到端事务驻留时间和最大 outstanding 数综合确定，通常会明显大于仅用于 TXREQ 排队的请求 Buffer。同时，统一结构需要区分待请求、待响应、待输出和可释放等状态，并处理入队、请求仲裁、响应更新及释放之间的并发访问和更新优先级，可能增加控制复杂度、组合路径和动态功耗，不利于高频实现。

如果解耦则可以将待请求拆分出来作为单独状态管理，链表则只需要维护保序以及发送仲裁即可
实现逻辑上的简化

再进一步，如果解耦的话，该如何拆分功能以简化逻辑？
目前所有的功能包括：保序下的qos分流、请求提交、流控、数据缓存、响应处理、发送仲裁。

从时序上来看，请求和响应构成串行关系，因此可以据此划分为请求部分以及响应部分两个流水级。请求部分主要实现qos分流、请求提交以及流控；响应部分主要实现数据缓存、响应处理以及保序发送仲裁。

至此，方案框架已经出来了，问题来到各自部分的实现方案如何权衡上：
从保序角度出发，有多种方案可以实现，本质上是确认自己是否可以发送（前序节点是否已发送）
从这一点出发，可能的方案分为指针类和查找类。指针类是在事务写入的时候确认前序节点，建立地址关联，在前序节点完成发送后更新状态，经典实现有fifo以及链表，好处是翻转率较低，但需要额外存储地址。查找类则不保存完整链路，而是根据状态或顺序信息判断当前谁可以执行，代价是大量组合逻辑以及更高的翻转率，好处是节省指针存储与管理逻辑。

总结下来有三个可行方案：

1. FIFO：通过存储位置维持顺序，天然保证全局顺序。一个 FIFO 可以容纳多个 AWID，但只能表达一条统一的出队顺序，独立调度能力较弱。
2. 链表：通过 head/next/tail 显式记录顺序。共享 Entry Pool 中可以同时维护多条按 AWID 划分的保序链。
3. CAM：不保存前后继指针，但仍需保存 AWID + age/sequence 等顺序信息。通过并行比较判断是否存在更早的同 AWID 事务，从而计算节点是否满足发送条件。

| 项目 | FIFO | 链表 | CAM前序检查 |
|---|---:|---:|---:|
| High QoS延迟 | 可能受队头阻塞，随深度增加 | 前序完成后可立即参与仲裁 | 前序完成后可立即参与仲裁 |
| 数据存储 | O(N×W) | O(N×W) | O(N×W) |
| 额外状态 | 读写指针、计数器 | head/tail/next/free-list | valid、age及比较结果 |
| 保序控制 | O(1) | O(1)，需直接索引表 | O(N²)比较 |
| 发送仲裁 | 单FIFO为O(1) | O(N)或维护ready队列 | O(N) |
| 随机释放 | 不支持 | 支持 | 支持 |
| 关键路径 | 短 | 中等 | 随N增长 |
| RTL复杂度 | 低 | 高 | 中 |
| 验证复杂度 | 低 | 高 | 中 |
| 深度扩展性 | 中 | 高 | 低 |

fifo相对于链表最大的优势是实现简单，状态翻转少。但其高qos最坏延迟大于链表
双方均采用N-1仲裁器的话，fifo的最坏延迟为（N+1）*Depth-1，链表的最坏延迟为Depth-1（同awid前序事务数量），高qos随着深度增加而递增

链表的核心优势是事务调度更灵活，qos与保序相互解耦，每个链头都可以根据自身qos来仲裁发送顺序，高qos的发送延迟较fifo更小，代价则是更高的翻转率以及更复杂的逻辑。
